## 一、功能机制（读插件源码实测，非文档自述）

### 1.1 设置项到 agent 的下发链

| 环节 | 位置 | 形态 |
|---|---|---|
| 设置字段 | `PluginSettings.kt:497` | `var sourceFrameSkipPrefixes: String = ""`（多行文本，一行一个前缀） |
| 设置面板 | `PluginSettingsPanel.kt:895-898` | 「SQL 日志」子页 →「源码位置捕获」分组末行 `JBTextArea(3, 24)` |
| 协议体 | `AgentProtocol.kt:55-63` | `{"disabled":…,"desensitize":…,"skipPrefixes":[…]}`，空列表省略键 |

| agent 接收 | `SenderLoop.extractSkipPrefixes` | 解析 `skipPrefixes` → `StackLocator.setExtraSkipPrefixes(String[])` |

### 1.2 agent 侧判定语义（`StackLocator.java`）

`isFrameworkFrame(className)` = 内置 `FRAME_SKIP_PREFIXES` 命中 **或** 用户登记 `EXTRA_SKIP_PREFIXES` 命中 **或** 类名含 `$Proxy`。

`locate()` 在 SQL 执行线程取栈快照，三层判定：

1. **L2 前缀名单**：`isFrameworkFrame` 命中的帧直接跳过（不进入候选池）；
2. **L1 来源过滤**：候选池中优先取「非 JAR 来源」帧（`ProtectionDomain.getCodeSource` 判目录/JAR）。开发态用户代码在 `target/classes` 目录 → 命中；
3. **安全网**：L1 无命中（fat jar 等）→ 取首个「带调试信息」的非框架帧。

**关键**：内置名单只收开源家族（JDK/驱动/池/ORM/Spring/`org.apache.`/`com.alibaba.` 等），**刻意不收通用工具库与公司自研包名**。故自研框架引擎帧全部进入候选池，L1 会取「最深的目录帧」＝引擎最深层方法——这就是「跳转恒落框架方法」的机制来源。登记前缀后这些帧在 L2 即被剔除，主位置自然落到业务帧。

**另一关键**：IDE 侧 `CallerSourceLocator.kt:36-42` 是**独立的硬编码名单**，不消费用户前缀——它只服务 MyBatis 拦截器链路。本功能**仅对 agent 增强捕获链路生效**，因此测试语料必须是「不经 MyBatis 的直连 JDBC」形态。

### 1.3 因此语料必须满足的条件

1. 引擎与业务代码**同处目录**（`target/classes`），引擎包名不在内置名单里 → 复现 L1 选中引擎帧；
2. 引擎**不经 MyBatis/MP**，走原生 JDBC（`JdbcTemplate`/`NamedParameterJdbcTemplate` + MySQL 驱动）→ 只有 agent 一条捕获链；
3. 业务调用形态**多样**，使登记前缀前后主位置差异可分辨、候选帧可对比；
4. 引擎包名前缀可一眼识别（插件设置 tooltip 自带示例 `com.corp.engine.`，本语料沿用同一根）。

## 二、语料设计

### 2.1 模拟自研框架（两个包根）

| 包根 | 角色 | 说明 |
|---|---|---|
| `com.corp.engine` | 数据访问引擎主体 | 静态门面 `DataUpdateTool`、Bean 门面 `DataQueryTool`、编排 `LocalDbService`、执行 `DmlRepository`、分页对象、函数式回调、JDK 代理工厂 |
| `com.corp.meta` | 共享元数据/分页工具库（被引擎依赖） | `FilterExpression` 条件树、`Q` 条件工厂、`SqlRenderer` 渲染、`MetaRegistry` 元数据、`PaginSupport` 分页包装并执行 |

分层（栈序，深→浅）：

```
com.corp.meta.PaginSupport#wrapAndQuery   ← 仅分页路径最深层（第二个前缀）
com.corp.meta.SqlRenderer#render          ← 渲染期，执行时不在栈上
com.corp.engine.DmlRepository#query       ← 普通路径最深层（第一个前缀）
com.corp.engine.LocalDbService#queryList
com.corp.engine.DataUpdateTool#findByFilter  ← 汇聚门面
<业务帧>                                   ← 登记前缀后的目标落点
```

**双前缀维度**：普通端点只需登记 `com.corp.engine.` 即落业务帧；分页端点最深层在 `com.corp.meta`，须**同时登记两行**才落业务帧——这是「前缀必须覆盖整条引擎链」的可复现证据。

统一前缀 `/selfdev`，全部返回原始 JSON（与兄弟模块一致，无包装体）。

## 五、风险与约束

| 风险 | 说明 | 缓解 |
|---|---|---|
| 前缀只对 agent 链路生效 | IDE 侧 `CallerSourceLocator` 不消费该设置 | 语料全部走原生 JDBC，不经 MyBatis；文档写明须开启「增强捕获」 |
| 引擎在目录 vs JAR | 若引擎被打成 JAR，L1 会自行过滤，前缀失去必要性 | 引擎与业务同模块同目录（`target/classes`），复现真实「同工程多模块」形态 |
| 本机无 MySQL | 端点全失败 | 本机 3306 已实测可用；`createDatabaseIfNotExist` + 自初始化降低环境要求 |
| 引擎包名撞内置名单 | 命中即被无条件跳过，用例失真 | 包根选 `com.corp.engine`/`com.corp.meta`，与内置名单逐条比对无交（已核 `com.alibaba.`/`org.apache.`/`com.google.`/`com.fasterxml.` 等） |
| 静态门面与 Spring 装配 | `com.corp.engine` 不在业务包扫描范围 | `@Import(EngineConfiguration.class)` 显式装配，模拟框架自带 auto-configuration |

### 7.3 实测帧落点（插桩取证，插桩代码已移除）

在 `DmlRepository#query` 与 `PaginSupport#wrapAndQuery` 临时插桩，按插件 `StackLocator` 同款前缀名单过滤栈帧，
以系统属性切换登记前缀，逐个场景实测：

| # | 用例 | 登记前缀 | 实测主位置 | 判定 |
|---|------|---------|-----------|------|
| 1 | `/style/static-call` | 无 | `com.corp.engine.DmlRepository#query` | 缺陷现象复现 ✅ |
| 2 | `/style/static-call` | `com.corp.engine.` | `SourceCaptureStyleServiceImpl#staticCall` | 正确 ✅ |
| 3 | `/query/paged` | 无 | `com.corp.meta.PaginSupport#wrapAndQuery` | 缺陷现象复现 ✅ |
| 4 | `/query/paged` | `com.corp.engine.` | `com.corp.meta.PaginSupport#wrapAndQuery` | **仍不对**（须第二前缀）✅ |
| 5 | `/query/paged` | `com.corp.engine.` + `com.corp.meta.` | `SourceCaptureQueryServiceImpl#paged` | 正确 ✅ |
| 6 | `/depth/deep-three` | `com.corp.engine.` | `DepthInnerServiceImpl#innerQuery`（候选含 middle/source/controller） | 正确 ✅ |
| 7 | `/depth/deep-three` | 再加 `cn.song.selfdevdemo.` | **候选池为空（poolSize=0）→ 无位置** | 误用后果 ✅ |

**场景 7 修正了计划 §2.2 的预期口径**：原写「落到更外层调用者甚至无位置」，实测是**直接无位置**——
业务帧被全部过滤后候选池为空，`locate()` 返回 null，跳转能力消失（不是降级到外层）。

### 7.4 实施中修掉的两个问题（均实测取证）

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | `/write/delete` 返回 500，`SQLSyntaxErrorException near 'p WHERE'` | MySQL 的 `DELETE` 不接受 `DELETE FROM tbl p` 形态的表别名 | `TableMeta` 增 `alias`/`deletable`，删除改走 `DELETE p FROM tbl p`（多表删除语法）；多表 JOIN 视图直接拒绝删除 |
| 2 | 库内中文全部乱码（`智能制造产线升级` → `鏅鸿兘鍒堕犱骇绾垮崌绾`） | `spring.sql.init` 未声明字符集时按平台默认读取脚本，Windows 为 GBK | `application.yml` 增 `spring.sql.init.encoding: UTF-8` |
