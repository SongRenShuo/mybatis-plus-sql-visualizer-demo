# 执行点在业务工具类（JAR 态）跳转上顶场景-开发计划

- **日期**：2026-09-23 15:20
- **目标**：给 `selfdev-framework-demo` 补一组场景，覆盖一条真实用户反馈的调用形状——**SQL 的执行点在业务自己的工具/构建类里，Service 只是它的调用方**；用户已按插件要求登记了公司工具库包名作「源码捕获帧过滤前缀」，但「跳转到 Java」落到了**上层 Service 里调用该工具类的那一行**，而不是工具类内部的 SQL 调用行。
- **范围**：demo 仓库新增一个 JAR 态语料子工程 `selfdev-shared-lib` + demo 侧 E 组 6 个端点（编号 28~33）；**不改插件代码**。
- **上游依据**：插件 agent `sub-projects/sql-visualizer-agent/.../util/StackLocator.java`（三层判定 + 整帧缓存）、IDE 侧 `EntryJumpResolver.kt` / `EntrySourceMatcher.kt#SourcePathResolver`（主位置解析失败 → 候选栈序回退）。
- **脱敏**：本计划与语料不引用任何真实项目名、包名、类名与表名，全部按 §六 的映射表替换。

---

## 一、现象拆解：「跳到父方法被调用的地方」在插件里只有三条生成路径

读 agent 与 IDE 侧源码可得，落点从「真实执行行」偏到「上层调用者」，可能且只可能由以下机制产生：

| # | 机制 | 触发条件 | 语料位 |
|---|------|---------|--------|
| A | **L1 来源过滤把 JAR 帧一律当第三方** | 业务工具类被打成依赖 JAR 运行（公司公共库 / 平台扩展包），其 `codeSource` 是 JAR；agent 的 L1 只认「目录帧 = 用户代码」，于是**从该帧往上顶**到第一个目录帧（调用方 Service） | E29（对照 E28） |
| B | **整帧缓存 key 只到 `class#method`** | 首个非框架帧是**共享帧**（平台内核 `execute`，或被多调用方共用的构建器方法），key 不含行号也不含完整链 → 先触发者的结果（文件+行+候选列）冻结服务给后触发者 | E30→E31（对照 E32→E33） |
| C | **IDE 侧主位置解析失败 → 候选回退** | 主位置相对路径在项目 base/模块 content root/source root 三级都拼不出文件（多源根、源码不在工程内），`EntryJumpResolver` 按候选栈序取首个可解析项——候选里第一个可解析的往往就是上层调用者 | 本轮不做语料（需构造非常规工程形态），留作作者用 info 日志排除 |

**「登记前缀」为什么救不了 A**：帧过滤前缀只有「跳过」语义，没有「提升为业务帧」的反向语义。
把 JAR 里那个业务包也登记进去，只会让它从候选池里消失，落点仍停在 Service——
E29 的第二档位就是用来钉死这个结论的。

**「登记前缀」为什么会放大 B**：用户登记了公司工具库包名（对应本语料的 `com.corp.platform.`），
首个非框架帧就从内核帧上移到构建器帧——如果构建器方法被多个调用方共用，key 依然共享，合流照旧；
如果用户**漏登记**了内核帧所在的包（真实项目里内核是另一个厂商的包名，极易漏），
key 就直接变成全应用共享的那一个 `execute`，A/B 两条机制同时命中。

## 二、语料设计：2×2 控制变量

### 2.1 两对逐行同构的类

| 角色 | JAR 态（`selfdev-shared-lib`） | 目录态（`selfdev-framework-demo`） |
|---|---|---|
| 平台内核帧（真正 `executeQuery()`） | `com.corp.platform.SqlKernel` | `cn.song.selfdevdemo.kernel.PlanTreeKernel` |
| 业务树构建器（**SQL 执行点所在**，两处调用点） | `com.corp.shared.util.PlanTreeQueryBuilder` | `cn.song.selfdevdemo.util.PlanTreeQueryBuilder` |

两对类的方法、SQL 文本、注释结构逐行对齐，唯一差异是**打包形态**。
构建器内部发出两处批查（形态对齐反馈里的「构建器开头两行批查、后续纯内存建树」），
Service 侧每个用例只有一行「调用构建器」。

### 2.2 端点矩阵（E 组，28~33）

| # | 端点 | 自变量 | 期望暴露 |
|---|------|--------|---------|
| 28 | `GET /selfdev/tool/directory-builder` | 目录态 + 单调用方 | **控制组**：登记 `cn.song.selfdevdemo.kernel.` 后落构建器两处调用行 |
| 29 | `GET /selfdev/tool/jar-builder` | **JAR 态** + 单调用方 | 机制 A：登记 `com.corp.platform.` 后仍落 Service 调用行；再登记 `com.corp.shared.util.` 结果不变 |
| 30 | `GET /selfdev/tool/jar-shared-first` | JAR 态 + 共用入口 | 与 31 成对，先触发者（其调用行进入整帧缓存） |
| 31 | `GET /selfdev/tool/jar-shared-second` | JAR 态 + 共用入口 | 机制 B：**跨文件串位**——31 的 SQL 跳到 30 的调用行 |
| 32 | `GET /selfdev/tool/dir-shared-first` | 目录态 + 共用入口 | 30 的对照组，先触发 |
| 33 | `GET /selfdev/tool/dir-shared-second` | 目录态 + 共用入口 | 30/31 的对照：合流是否只在 JAR 侧发生（预期：目录态同样合流 ⇒ B 与来源无关，纯 key 粒度问题） |

**执行序**（决定可观察性）：30 与 31、32 与 33 必须按编号先后触发，且中间**不重启应用**——
整帧缓存是 agent 进程内的静态表，重启即清空。

## 五、风险与约束

- IDEA 的 Maven workspace 解析会把 `selfdev-shared-lib` 依赖还原成兄弟模块的 `target/classes`
  （目录形态），JAR 档位需 `install` + `Unload Projects`（或单模块 `spring-boot:run`）才生效——
  已写进 `selfdev-shared-lib/README.md`。这一「退化」本身可当反向证据用。
- 帧落点实证复刻了 agent 的判定规则，规则一旦在插件侧变更需同步；已在探针输出里标注规则来源文件。
- 语料刻意不使用 MyBatis：MyBatis 拦截器链路（`CallerSourceLocator`）不消费帧过滤前缀，混用会污染判定链路。

### 7.2 取证方法（复刻 agent 判定，非推断）

不启 IDEA、不装插件：用 `java.lang.reflect.Proxy` 造一个 stub `DataSource → Connection → PreparedStatement`，
在 `executeQuery()` 被调用的那一刻取 `Thread.currentThread().getStackTrace()`——
这与 agent 织入点（驱动 `Statement#execute`）同深，其下的驱动/池帧本就在 L2 名单里、不影响判定。
随后逐字套用 `StackLocator` 的三层判定：L2 名单（内置 + 用户前缀 + `$Proxy`）→
L1 来源过滤（`Class.forName(cn,false,loader).getProtectionDomain().getCodeSource()` 判目录/JAR）→
上顶收敛 → `candidates`（≤8，排除主位置文件）→ **整帧缓存**（仅 `via=L1` 写入，key = 首个非框架帧 `class#method`）。

同一份语料跑两档 classpath 构成唯一自变量：

- `mode=dir`：`selfdev-shared-lib/target/classes`（目录）
- `mode=jar`：本地仓库里的 `selfdev-shared-lib-1.0.0.jar`（JAR）——输出首行打印实际来源 URL 以自证

| 档位 | 用例 | 实测主位置 | 判定 |
|---|---|---|---|
| P0 不登记 | 28 目录态·SQL① | `cn/song/selfdevdemo/kernel/PlanTreeKernel.java:100` | 既记缺陷现象「跳转恒落框架方法」复现 ✅ |

| P1 登记内核层 | 28 目录态·SQL① | `cn/song/selfdevdemo/util/PlanTreeQueryBuilder.java:52` = 调用点①（候选含 Service:46） | **正确落点** ✅ |
| P1 登记内核层 | 28 目录态·SQL② | `CACHE-HIT → PlanTreeQueryBuilder.java:52`（自身应为 `:67`） | **机制 B：同一方法内两处调用点互相串位** ✅ |
| P1 登记内核层 | 29 JAR 态·SQL① | `.../SourceCaptureToolSiteServiceImpl.java:62`（候选含真执行点 `PlanTreeQueryBuilder.java:38`） | **用户现象单一变量复现：落到「父方法被调用的地方」** ✅ |
| P1 登记内核层 | 30 JAR 态·先触发 | `.../SourceCaptureToolSiteServiceImpl.java:74` | 基准 |
| P1 登记内核层 | 31 JAR 态·后触发 | `CACHE-HIT → ...Service.java:74`（自身调用行是 `:86`） | **机制 B：跨文件串位**（与反馈同形）✅ |
| P1 登记内核层 | 32→33 目录态对照 | 32 = `util/PlanTreeQueryBuilder.java:94`；33 = `CACHE-HIT → :94` | 合流**与帧来源无关**，只与 key 粒度有关 ✅ |
| P2 再登记构建器包 | 29 JAR 态 | 仍 `.../SourceCaptureToolSiteServiceImpl.java:62`，`pool` 由 2 收缩为 1 | **前缀只有「跳过」语义：登记 JAR 业务包不能把落点送回去** ✅ |
| P2 再登记构建器包 | 30→31 | key 变成各自的 Service 方法 → 不再串位（31 落 `:86`） | 合流的必要条件是「共享 key」✅ |

### 7.4 三条结论（供作者定谳用）

1. **机制 A（L1 来源过滤）足以单独造出「跳到父方法调用处」**，且发生在用户登记任何前缀**之前**：
   JAR 里的业务帧与 JAR 里的内核帧被一并判为第三方，主位置取栈序上第一个目录帧＝调用方 Service。
   真实项目若扩展业务代码以 JAR 形态部署（低代码平台常见），则整条业务链都在 JAR 里，
   落点取决于「哪一帧的代码路径能在工程里解析到」——需用户侧 `logLevel=info` 的
   `pool=[帧 jar=true/false]` 打点定谳（本轮按约定未取证）。
2. **机制 A 的正确答案其实躺在候选列里**：实测 29 的 `candidates` 首项就是真执行点
   `com/corp/shared/util/PlanTreeQueryBuilder.java:38`。而 IDE 侧 `EntryJumpResolver`
   只在**主位置解析失败**时才查候选——主位置命中 Service 后回退链被短路。
   可评估的修法方向（不限于此）：L1 因来源过滤上顶时，若候选中存在更深的、
   其源码在工程内可解析的帧，则优先该候选或在面板上提示「执行点位于 JAR 帧 …」。
3. **机制 B（整帧缓存 key 只到 `class#method`）与打包形态无关**：目录态与 JAR 态都实测串位，
   同方法内两处调用点（28）与跨文件两个调用方（30/31）都命中；
   一旦把共享帧所在包登记进前缀、使 key 上移到各自的业务方法（P2 档），串位即消失——
   与 T-SourceJumpFunnel P0-3「缓存防合流」的既有结论一致：**残余合流面的边界是 key 粒度**，
   不是缓存写入路径。
