# 执行点在业务工具类（JAR 态）跳转上顶场景-开发计划

- **日期**：2026-09-23 15:20
- **目标**：给 `selfdev-framework-demo` 补一组场景，覆盖一条真实用户反馈的调用形状——**SQL 的执行点在业务自己的工具/构建类里，Service 只是它的调用方**；用户已按插件要求登记了公司工具库包名作「源码捕获帧过滤前缀」，但「跳转到 Java」落到了**上层 Service 里调用该工具类的那一行**，而不是工具类内部的 SQL 调用行。
- **范围**：demo 仓库新增一个 JAR 态语料子工程 `selfdev-shared-lib` + demo 侧 E 组 7 个端点（编号 28~34）；**不改插件代码**。
- **上游依据**：插件 agent `sub-projects/sql-visualizer-agent/.../util/StackLocator.java`（三层判定 + 整帧缓存）、IDE 侧 `EntryJumpResolver.kt` / `EntrySourceMatcher.kt#SourcePathResolver`（主位置解析失败 → 候选栈序回退）。
- **脱敏**：本计划与语料不引用任何真实项目名、包名、类名与表名，全部按 §六 的映射表替换。

## 一、现象拆解：「跳到父方法被调用的地方」在插件里的四条生成路径

读 agent 与 IDE 侧源码可得，落点从「真实执行行」偏到「上层调用者」，只可能由以下机制产生：

| # | 机制 | 触发条件 | 语料位 |
|---|------|---------|--------|
| A | **L1 来源过滤把 JAR 帧一律当第三方** | 业务工具类被打成依赖 JAR 运行（公司公共库 / 平台扩展包），其 `codeSource` 是 JAR；agent 的 L1 只认「目录帧 = 用户代码」，于是**从该帧往上顶**到第一个目录帧（调用方 Service） | E29（对照 E28）——**当前仍未修** |
| B | **判定缓存把「同身份」的行号冻结**（历史形态） | ≤ v2026.9.18 把结果帧整帧入缓存，key = 首个非框架帧 `class#method` | E28 两处调用点、E30→E31、E32→E33——**v2026.9.23 由 T-AgentSourceLocateStale T-01 根治**（只缓存判定 + 行号按当前栈现算 + 身份在场校验），本组用例转为**回归护栏** |
| **B′** | **T-01 的「身份在场」校验粒度不足：祖先帧必然在场** | 共享 `entryKey` 的判定被写成某个**浅帧**身份（典型：Service 方法自己直发过一条 SQL，此时它是最深目录帧）；之后经业务工具类发的 SQL，其栈上该 Service 帧是**祖先帧、一定在 pool 里** ⇒ 校验通过 ⇒ 主位置仍被钉在浅帧，行号现算出来恰好是「调用工具类」那一行 | **E34（混合来源：业务在目录 + 内核在 JAR）——当前仍活，且最贴近用户现场** |
| C | **IDE 侧主位置解析失败 → 候选回退** | 主位置相对路径在项目 base/模块 content root/source root 三级都拼不出文件（多源根、源码不在工程内），`EntryJumpResolver` 按候选栈序取首个可解析项——候选里第一个可解析的往往就是上层调用者 | 本轮不做语料（需构造非常规工程形态），留作作者用打点排除 |

**「登记前缀」为什么救不了 A**：帧过滤前缀只有「跳过」语义，没有「提升为业务帧」的反向语义。
把 JAR 里那个业务包也登记进去，只会让它从候选池里消失，落点仍停在 Service——
E29 的第二档位（P2）就是用来钉死这个结论的。

**B′ 为什么可以靠「补登记内核包名」缓解**：把平台内核包名登记进前缀后，共享 `entryKey`
不再是引擎的 `execute`，而是各业务方法自己 ⇒ 判定不再被一个祖先浅帧长期占用
（E34 在 P1 档实测回到构建器真执行点）。代价：若某条 SQL 栈上除引擎帧外没有目录帧，
会退到「候选池为空 → 无位置」（§三 已记该误用后果）。

## 二、语料设计：三路控制变量

### 2.1 两对逐行同构的类

| 角色 | JAR 态（`selfdev-shared-lib`） | 目录态（`selfdev-framework-demo`） |
|---|---|---|
| 平台内核帧（真正 `executeQuery()`） | `com.corp.platform.SqlKernel` | `cn.song.selfdevdemo.kernel.PlanTreeKernel` |
| 业务树构建器（**SQL 执行点所在**，两处调用点） | `com.corp.shared.util.PlanTreeQueryBuilder` | `cn.song.selfdevdemo.util.PlanTreeQueryBuilder` |

两对类的方法、SQL 文本、注释结构逐行对齐，唯一差异是**打包形态**。
构建器内部发出两处批查（形态对齐反馈里的「构建器开头两行批查、后续纯内存建树」），
Service 侧每个用例只有一行「调用构建器」。

## 五、风险与约束

- IDEA 的 Maven workspace 解析会把 `selfdev-shared-lib` 依赖还原成兄弟模块的 `target/classes`
  （目录形态），JAR 档位需 `install` + `Unload Projects`（或单模块 `spring-boot:run`）才生效——
  已写进 `selfdev-shared-lib/README.md`。这一「退化」本身可当反向证据用。
- 帧落点实证复刻了 agent 的判定规则，规则一旦在插件侧变更需同步；已在探针输出里标注规则来源文件。
- 语料刻意不使用 MyBatis：MyBatis 拦截器链路（`CallerSourceLocator`）不消费帧过滤前缀，混用会污染判定链路。

### 7.2 取证方法（复刻 agent 判定，非推断）

不启 IDEA、不装插件：用 `java.lang.reflect.Proxy` 造一个 stub `DataSource → Connection → PreparedStatement`，
在 `executeQuery()` 被调用的那一刻取 `Thread.currentThread().getStackTrace()`——
这与 agent 织入点（驱动 `Statement#execute`）同深，其下的驱动/池帧本就在 L2 名单里、不影响判定。
随后逐字套用 `StackLocator` 的三层判定：L2 名单（内置 + 用户前缀 + `$Proxy`）→
L1 来源过滤（`Class.forName(cn,false,loader).getProtectionDomain().getCodeSource()` 判目录/JAR）→
上顶收敛 → `candidates`（≤8，排除主位置文件）→ **判定缓存**（key = 首个非框架帧 `class#method`）。

同一份语料跑两档 classpath 构成唯一自变量：

- `mode=dir`：`selfdev-shared-lib/target/classes`（目录）
- `mode=jar`：本地仓库里的 `selfdev-shared-lib-1.0.0.jar`（JAR）——输出首行打印实际来源 URL 以自证

> **版本对齐留痕**：取证过程中插件仓库已前进到 v2026.9.23，其中 T-AgentSourceLocateStale T-01
> 把「整帧结果入缓存」改成「只缓存判定（via + 主位置身份）+ 行号按当前栈现算 + 身份在场校验」。
> 故 §7.3 按**当前规则**重跑，§7.4 单列旧规则结果做对照——不把已修的缺陷当新问题报给作者。

### 7.5 结论（供作者定谳用）

1. **用户现场最匹配的是机制 B′，且它在 v2026.9.23 仍然活着**（E34 实测）：
   同一个 Service 方法先直发一条 SQL、再调业务工具类发第二条时，第一条把「最深目录帧＝该 Service 方法」
   写进共享 `entryKey` 的判定缓存；第二条的栈上该方法是**祖先帧、必然在场** ⇒
   「身份在场」校验通过 ⇒ 主位置被钉在 Service，行号按当前栈现算＝它调用工具类的那一行。
   这与反馈里「跳到父方法被调用的地方」逐字吻合，也解释了为什么登记公司工具库包名（跳过 `DataUpdateTool`
   那一层）不影响、也不解决问题——共享 `entryKey` 是**更下面那层引擎帧**。
   真机佐证（名称已脱敏）：`entry=<平台引擎的字典服务帧>#search…`、
   `primary=<业务工具类>:309 (<工具类>#convert…)`、`via=L1` ——
   该条落点本身正确（那一行确实在调字典工具类），但证明了 `entryKey` 就是平台引擎的共享帧。
2. **机制 A 同样未修**（E29 实测，P0/P1/P2 三档同一落点）：业务工具类一旦以 JAR 形态运行，
   就被 L1 判成第三方帧，主位置上顶到第一个目录帧；登记该 JAR 包名只会让它从候选池消失，落点不变。
   两者在面板上表现一模一样（都是「落到调用方那一行」），**区分办法**：看真执行点是否出现在候选列里
   ——机制 A 的候选含 JAR 帧路径，机制 B′ 的候选含目录内那行真执行点。
3. **修法线索（按代价从小到大）**：
   ① 文档/设置项 tooltip 提示「须把**整条**引擎链的包名登记全」（本模块 §三 已有同款结论，E34 的 P1 档实证有效）；
   ② 判定缓存命中后，不要因「身份在场」就直接采用：在当前 pool 里同时找「首个目录帧」，
   若它比缓存身份**更深**则用更深者并刷新判定（E34 的 P0→P1 差异给了可回归的最小形状）；
   ③ 钉住发生时**真执行点其实一直在候选列里**（E34 第 3 项、E29 首项），可考虑面板提示或让
   `EntryJumpResolver` 在主位置为祖先帧时也展示候选；
   ④ 若要根治 A，需要「把指定 JAR 包登记为业务帧」的反向名单——现设置项只有「跳过」语义。
4. **真机取证口径**：`logLevel` 是 agent 启动参数，插件 `AgentProtocol.agentArgs(port)` 固定注入
   `logLevel=warn`，`AgentArgs` 只解析该字符串、**无设置项也无系统属性覆盖口** ⇒
   `StackLocator.diagnose()` 的 pool 打点真机不可达；且端口是 `ServerSocket(0)` 运行时协商，
   手写 `-javaagent` 也接不上 IDE。可用证据是**与档位无关**的一次性摘要
   `[T-AgentSourceLocateStale] 入口键非业务帧…`（T-05），按 entryKey 去重，
   建议重启应用后只触发一次目标接口再看控制台。
