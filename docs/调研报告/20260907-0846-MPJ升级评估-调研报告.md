# MPJ升级评估-调研报告

- **日期**：2026-09-07
- **评估对象**：mybatis-plus-join-demo 的 MPJ 1.5.8 → 1.5.9 升级可行性
- **结论**：**不升级，维持 1.5.8**。1.5.9 对插件识别面（Wrapper/Service 链 API）零增量，但运行期基建发生迁移（基类改挂 MP 3.5.9+ 新架构包、注入器签名变更、adapter 重组），必须配 MP 3.5.17+ 使用，与 demo 的 MP 3.5.2 基线相悖。原「selectSum 族需 MPJ ≥ 1.5.9」的版本墙为误报，聚合族与 selectIgnore 在 1.5.8 已全部可用，语料已直接补齐（无需升级）。
- **插件用户视角**：使用 MPJ 1.5.9+ 对插件识别与预览**无影响**（详见 §六）。

## 一、评估方法

1. Maven Central（aliyun 镜像）确认 1.5.9 为最新 release（2026-07-10 发布，无 1.6.x 线）。
2. 下载 1.5.9 全套构件（boot-starter/core/extension/annotation），与本地 1.5.8 做**三重全量比对**：
   - join-core 类清单 diff（unzip -l 全列）；
   - Query 接口方法清单 diff（javap 全列）；
   - MPJQueryWrapper（字符串链）方法清单 diff。
3. javap 核对各争议 API 的存在性与签名。
4. 查阅插件《MP-MPJ官方API覆盖矩阵》§2.7 版本配对口径。

## 二、比对结果

第一轮三重比对（类清单 / Query 接口 / MPJQueryWrapper 方法）零差异；追加**全类方法级 diff**（两版 join-core 全部类 javap 逐类比对，约 4000 行签名）后确认：

| 比对面 | 1.5.8 vs 1.5.9 |
|--------|----------------|
| join-core 类清单 | 零差异（无新增/删除类） |
| extension 类清单 | 零差异 |
| **插件识别面**：Query 接口、MPJQueryWrapper、Compare*/Join 条件接口（Wrapper 链构建 API） | **零差异** |
| **运行期基建**（method/repository/base/injector 包） | **有实质变更**，见下 |

运行期基建变更明细（全类 diff 唯一差异集，共 18 行签名）：
1. 基类包名迁移：`MPJBaseService` / `MPJBaseServiceImpl` / `JoinCrudRepository` 的父级从 `com.baomidou.mybatisplus.extension.service.IService` / `...extension.service.impl.ServiceImpl` / `...extension.repository.CrudRepository` 迁至 `com.baomidou.mybatisplus.spring.*`（MP 3.5.9+ 新架构包名）——这正是 1.5.9 配对 MP 3.5.17+ 的原因；
2. `MPJSqlInjector.getMethodList(Class)` / `getMethodList(Class, TableInfo)` 两重载移除（跟随 MP 3.5.17 注入器签名变化）；
3. `MPJAbstractMethod` 父类从 `adapter.v352.AbstractMethod352` 改为 MP core `AbstractMethod`（版本 adapter 机制重组）；
4. 注入方法类（SelectJoinList/One/Count/Page、UpdateJoin/UpdateJoinAndNull/DeleteJoin）公共默认构造器移除（内部化）。

**对评估结论的影响**：变更全部位于运行期基建，Wrapper 链构建 API 与方法名零变化——不升级的结论不变且更强（1.5.9 强绑定 MP 3.5.9+ 新架构）。

## 三、版本墙勘误（第二轮误报更正）

上一轮 README/计划文档标注「selectSum/Max/Min/Avg/Len 族需 MPJ ≥ 1.5.9」为**误报**，成因是早期 javap 方法名 grep 模式有损（`[a-zA-Z]+\(java` 只匹配到参数以 java 开头的方法，泛型参数 `com.baomidou...` 开头的聚合方法全部漏报）。经精确 javap 复核：

- `selectSum/selectMax/selectMin/selectAvg/selectLen`：各 3 重载 `(列)`、`(列, 别名字符串)`、`(列, 别名SFunction)`，**1.5.8 已有**（与矩阵「既有能力」标注一致）；
- `selectIgnore(String...)`：**字符串链 MPJQueryWrapper 专属方法，1.5.8 已有**（矩阵「selectIgnore（字符串链）」表述准确）；
- `selectIgnore` 在 lambda 链 Query 接口上两版均无——若语料需要 lambda 链剔除列，用 `select` 反选或 `selectFilter` 替代。

## 四、配对口径

矩阵 §2.7：MPJ 1.5.8 ↔ MP 3.1.2 ~ 3.5.16；MPJ 1.5.9 ↔ MP 3.5.17+（其 root pom 编译基线 mybatis.plus.version=3.5.17，MP 依赖为 provided）。

join-demo 现状为 MP 3.5.2 + MPJ 1.5.8，处于 1.5.8 官方配对区间内。若强升 1.5.9：
1. API 无任何收益（零增量）；
2. 配对口径出窗（MP 3.5.2 ∉ 1.5.9 目标区间），运行期 adapter 行为无官方背书；
3. 若为配对把 MP 同步升到 3.5.17，则破坏「旧版本对照基线」的建仓初衷，且回归面覆盖全部 MPJ 语料。

## 五、结论与动作

1. **维持 MPJ 1.5.8**，未来仅在真实项目 MP 基线整体上移时同步评估。
2. 已直接在 1.5.8 上补齐聚合语料：`aggregateExt` 增 selectSum/selectMax/selectMin/selectAvg/selectLen（三重载形态），`queryStringExt` 增字符串链 `selectAll + selectIgnore`。
3. README 版本说明已同步勘误。

## 六、插件用户使用 MPJ 1.5.9+ 是否受影响

**结论：对插件的 SQL 识别、预览与参数回填无影响，1.5.9+ 用户恰好是插件的最佳支持档。**

1. 插件是 PSI 静态分析，不加载用户工程 classpath；解析规则按「最新稳定版方法名超集」收录，矩阵即以 MPJ 1.5.9（当前最新 release）为基线核验——1.5.9 用户的代码形态就是插件规则的建模原形。
2. 插件识别面 = Wrapper 链构建 API + service 链方法名 + 终结点/CRUD 方法名。§二全类方法级 diff 证明该面在 1.5.8→1.5.9 完全一致；有变化的只是注入器/基类等运行期基建，插件不感知。
3. 基类迁移（extension.* → spring.*）只改变用户工程的运行时装配（强制配 MP 3.5.17+ 新架构），不改变源码文本形态：用户写的仍是 `extends MPJBaseServiceImpl`、`service.lambdaQuery()...`、`JoinWrappers.lambda(...)`，插件按名字匹配，与 classpath 无关。
4. 注入方法名（selectJoinPage/One/Count、updateJoinAndNull、deleteJoin）未变，插件终结点/CRUD 名单继续命中。
5. 唯一的未来影响窗口：1.5.10+/1.6.x 若新增 wrapper 方法名，需插件把新名字纳入分派集（常规版本跟进，插件自带更新检查）。截至今日 1.5.9 即最新，窗口不存在。
6. 反方向同样安全：低版本（1.5.6/1.5.8）用户是插件方法名超集的子集，天然兼容——本 demo 仓库维持 1.5.8 语料即为该兼容性的持续验证样本。
